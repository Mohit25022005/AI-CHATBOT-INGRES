# INGRES DATABASE COMPREHENSIVE KNOWLEDGE BASE

## SECTION 1: WHAT IS INGRES DATABASE

### Overview and Definition
Ingres Database is a proprietary SQL relational database management system (RDBMS) intended to support large commercial and government applications. Actian Corporation controls the development of Ingres and makes certified binaries available for download, as well as providing worldwide support.

Ingres is called a Relational Database Management System (RDBMS) because of the way it handles information. Breaking down this term:
- A DATABASE is a set of related information that Ingres stores for you in a computer.
- A MANAGEMENT SYSTEM lets you put data into your databases (to add new customers, for example) or retrieve data from it (to produce a report of all items sold last month).
- Ingres is a SYSTEM because you can combine its different components to organize and access your data in the way that works best for you.
- RELATIONAL means Ingres stores your data in tables that make it easy for you to see how the various pieces of information relate to each other.

### Historical Background
Ingres began as a research project at the University of California, Berkeley, starting in the early 1970s and ending in 1985. When two Berkeley professors, Michael Stonebraker and Eugene Wong, read papers about IBM's System R project in 1973, they became interested in applying those concepts and started a relational database research project of their own.

The original code was available at minimal cost under a version of the BSD license. During its early years, Ingres remained largely similar to IBM's System R in concept but differed in providing QUEL as a query language instead of SQL initially. It was based largely on DEC machines, both under UNIX and VAX/VMS.

### Current Status and Versions
Today, Actian Ingres is a hybrid transactional/analytical processing database with record-breaking performance. The latest major release is Ingres 12.0, launched in June 2024. The database is currently in use by more than 3,000 customers worldwide, including Lufthansa Systems, The Irish Office of Revenue Commission, and Capita Software Services.

Ingres has evolved through several major versions:
- Ingres 11.0 (includes IngresConnect, EMA)
- Ingres 11.2 (includes JSON support, data masking)
- Ingres 12.0 (latest, with enhanced performance, backup to cloud, disaster recovery, and workload automation)

Ingres 12.0 was also previously known commercially as Actian X Hybrid Database, and more recently as HCL Actian Ingres.

### Architecture and Design
Ingres supports both row-based and columnar storage formats, using its ultra-reliable enterprise transactional database engine and Vector's X100 analytics engine. This combination allows organizations to perform transaction processing and operational analytics easily and efficiently within a single database.

The system is mainly intended for OLTP (Online Transaction Processing) tasks, but the latest versions have support for columnar storage which is suitable for OLAP (Online Analytical Processing) tasks. This hybrid capability refers to performing both OLTP and OLAP tasks by employing a hybrid storage model (both row and column), though it is still disk-oriented.

## SECTION 2: INSTALLATION AND SETUP

### Pre-Installation Requirements

**System Requirements:**
- Verify that hardware and software meet Ingres requirements as documented in the platform-specific Readme
- Root access required for installation on Linux systems
- Administrator privileges required for Windows installation

**Planning Decisions:**
Before installation, decide on the following critical parameters:

1. **Installation Type:**
   - Server Installation: Full database server with all components
   - Client Installation: Client-only installation without database, allows access to remote Ingres servers

2. **Installation ID:**
   - Consists of two case-sensitive characters, starting with a letter
   - Default is "II"
   - Used to calculate which ports the Ingres servers will listen on
   - Multiple installation IDs can be used on one machine

3. **File Locations:**
   - II_SYSTEM: System files location
   - Transaction log location and size
   - Checkpoint location
   - Journal location
   - Work location
   - Dump location

4. **Database Configuration:**
   - Expected number of concurrent users (default: 32)
   - SQL-92 compatibility mode
   - Character set (e.g., KANJIEUC for Tokyo)
   - Timezone configuration
   - Number of CPUs

### Installation Components

**Core Components:**
- Intelligent DBMS: The database engine
- Terminal Monitors: Forms-based and command line SQL interfaces
- Querying and Reporting Tools: Report-writing and report-running tools
- Forms Editor

**Additional Components (Full Version):**
- Net: Makes it possible for Ingres utilities and applications to access databases on different installations
- Replicator: Support for replication functions
- Star: For handling distributed databases
- Enterprise Access: Communication with different DBMS and non-relational data sources
- Protocol Bridge: For communicating with clients on different network types
- Spatial Object Library: For handling two-dimensional spatial objects
- Internet Commerce Enabled (ICE): Ingres' proprietary CGI solution
- Enhanced Security: Tool supporting mandatory access control
- C2 Security Auditing: C2 level auditing capability

**Separately Installable Components:**
- Ingres .NET Data Provider
- Ingres Documentation
- OpenROAD 12.0 (for application development)

### Linux Installation Process

**Method 1: Using Installation Wizard**
1. Ensure you have root access
2. Run the ingres_install script located in the root directory of the Ingres distribution
3. The Ingres Installation Wizard will be displayed
4. Follow the wizard dialogs to provide required information
5. The installation program will install Ingres automatically

**Method 2: Using RPM from Command Line**
Installation of Ingres on Linux uses RPM Package Manager. You can install directly using RPM commands without the wizard if you're familiar with RPM.

**Using Response Files:**
For automated or custom installations, set the II_RESPONSE_FILE environment variable to point to a response file containing configuration settings.

Example response file for Tokyo location with one CPU and KANJIEUC character set:
```
# System files on default location
# Checkpoint, journal, work, dump, and transaction log in II_SYSTEM
II_INSTALLATION=II
II_TIMEZONE_NAME=ASIA-TOKYO
II_CHARSET=KANJIEUC
II_NUM_OF_PROCESSORS=1
```

Example response file for New York with two CPUs, 500 MB transaction log, ANSI/ISO Entry SQL-92 standard:
```
II_INSTALLATION=II
II_TIMEZONE_NAME=NA-EASTERN
II_DATE_FORMAT=US
II_NUM_OF_PROCESSORS=2
II_LOG_FILE_SIZE_MB=500
II_ENABLE_SQL92=YES
```

### File System Structure

**Important Paths (created during installation):**
- II_SYSTEM: Main system directory (e.g., /opt/Ingres/IngresII on Linux)
- II_DATABASE: Data files location
- II_CHECKPOINT: Checkpoint files location
- II_JOURNAL: Journal files location
- II_WORK: Work files location
- II_DUMP: Dump files location
- II_LOG_FILE: Transaction log file location
- II_DUAL_LOG: Dual transaction log location (if enabled)

**Database File Types:**
1. **Control File:** Stores basic information about the database
2. **Data Files:** Every system table, user table, and index in separate files
3. **Checkpoint Files:** Database backup files (may consist of multiple files)
4. **Dump Files:** Before-images of changed data blocks during online backups
5. **Journal Files:** Records of committed transactions from the log file
6. **Work Files:** Temporary files created for sorting large data volumes

### Database Locations
Ingres uses "locations" to specify directories for different file types:

- **System Location:** For system files
- **Data Location:** For data files of a database
- **Checkpoint Location:** For checkpoint files
- **Journal Location:** For journal files
- **Work Location:** For temporary work files
- **Dump Location:** For dump files during online checkpoints

### Transaction Log Configuration

**Log File Characteristics:**
- Location and size can be changed at any time after installation
- Method for changing is described in the System Reference Guide

**Dual Logging (Log Mirroring):**
- Recommended for production systems
- If log gets corrupted, Ingres stops and databases must be recovered from backup
- In live systems, use either RAID protection or Ingres dual logging
- Dual log copy found under II_DUAL_LOG/ingres/log named dual_log
- Not always necessary in development or test environments

- Object names not protected by quotes are converted to lowercase (SQL-92 converts to uppercase)
- Other differences documented in SQL Reference Guide
- Can be configured for full SQL-92 compatibility during installation

### Installation Instances
An Ingres installation (or instance) is:
- A collection of server processes
- Shared memory segments
- Semaphores for inter-process communication
- Disk files used for transaction processing and recovery

**Instance Characteristics:**
- One installation can support multiple databases
- Each database can be owned by any user known to the installation
- Multiple databases can be accessed simultaneously
- Number of databases is configurable
- Databases are not pre-sized and can grow as disk space allows
- Multiple installation IDs can be used on one machine (e.g., for running more than 8 processes)

## SECTION 3: KEY TECHNICAL CONCEPTS

### Database Architecture

**Storage Models:**
Ingres supports hybrid storage architecture combining:

**Processing Engines:**

### Transaction Management

**ACID Compliance:**
Ingres is fully ACID compatible and is fully transactional, including all DDL (Data Definition Language) statements.

**Transaction Processing Features:**
- Full transactional support
- Distributed transaction processing
- Two-phase commit protocol
- Transaction logging to journal files
- Automatic recovery mechanisms

### Checkpointing (Backup) System

**Offline Checkpointing:**
- Requires all users to disconnect from database
- Acquires global lock on entire database
- Performs backup on all data
- More comprehensive but results in downtime

**Online Checkpointing:**
- Default checkpointing scheme
- Users do not need to disconnect
- Faster than offline checkpointing with less downtime
- Still blocking - users cannot proceed until consistent point is created
- DBMS records all changes but does not support operations like DROP or CREATE during checkpoint
- Changed data blocks (pages) saved in dump files to ensure consistency

### Journaling System

**Purpose:**
- Protects installation against media failures
- Allows database restoration to last committed state
- Works with checkpoints for point-in-time recovery

**Process:**
- Ingres periodically writes committed transaction records from log file to journal files
- Frequency is tunable based on amount of information written to transaction log
- Can be enabled/disabled at database or table level
- Default behavior is journaling enabled

**Recovery Scenarios:**
- If database disk crashes: Restore from checkpoint + apply journal files
- If log disk fails: Restore to state at time of last journal file

### Data Compression

**Supported Compression:**
- Compression works on character and text columns only
- Trailing nulls and blanks are compressed
- Non-nullable types (Integer, floating point, date) are NOT compressed
- No other compression schemes mentioned in documentation

## SECTION 11: SQL AND QUERY LANGUAGE

### SQL Support

**SQL Implementation:**
Ingres originally used QUEL (Query Language) but switched to SQL as the primary query language. The current implementation supports:

- Standard SQL syntax
- SELECT, INSERT, UPDATE, DELETE operations
- Data Definition Language (DDL)
- Data Manipulation Language (DML)
- Data Control Language (DCL)
- Transaction control statements

**SQL-92 Compliance:**
- Configurable SQL-92 compatibility mode
- Default mode differs slightly from SQL-92
- Object names converted to lowercase (not uppercase as in SQL-92)
- Can be configured for full compliance during installation

### Data Types

**Numeric Types:**
- INTEGER: 4-byte signed integer
- SMALLINT: 2-byte signed integer
- BIGINT: 8-byte signed integer
- DECIMAL/NUMERIC: Fixed-point decimal
- FLOAT: Floating-point number
- REAL: Single-precision floating point
- DOUBLE PRECISION: Double-precision floating point

**String Types:**
- CHAR(n): Fixed-length character string
- VARCHAR(n): Variable-length character string
- NCHAR(n): National character set fixed-length
- NVARCHAR(n): National character set variable-length
- TEXT: Large text objects
- LONG VARCHAR: Variable-length strings up to 2GB

**Date and Time Types:**
- DATE: Calendar date
- TIME: Time of day
- TIMESTAMP: Date and time combination
- INTERVAL: Time interval

**Binary Types:**
- BYTE: Binary data
- BYTE VARYING: Variable-length binary
- LONG BYTE: Large binary objects

**Special Types:**
- BOOLEAN: True/false values
- JSON: JSON data type (Ingres 11.2+)
- Spatial data types (with Geospatial support)

### Transaction Control

**Transaction Statements:**
```sql
BEGIN TRANSACTION;
COMMIT;
ROLLBACK;
SAVEPOINT savepoint_name;
ROLLBACK TO SAVEPOINT savepoint_name;
```

**Transaction Characteristics:**
- All DDL statements are transactional
- Full ACID compliance
- Multi-statement transactions
- Savepoint support for partial rollback
- Distributed transaction support with two-phase commit

### Stored Procedures and Functions

**Database Procedures:**
Ingres supports stored procedures written in SQL and embedded programming languages. Procedures can:
- Accept input parameters
- Return output parameters
- Execute complex business logic
- Improve performance by reducing network traffic
- Encapsulate business rules

**Triggers:**
Database triggers can be created to:
- Execute automatically on INSERT, UPDATE, or DELETE
- Enforce business rules
- Maintain data integrity
- Audit data changes
- Implement complex constraints

### Indexes

**Index Types:**
- B-tree indexes (default)
- Hash indexes
- RTREE indexes (for spatial data)
- Unique indexes
- Composite indexes (multiple columns)

**Index Usage:**
- Automatically used by query optimizer

## SECTION 15: DISTRIBUTED DATABASES

### Ingres Star

**Overview:**
Ingres Star provides distributed database capabilities, treating enterprise data as a single global database regardless of physical location.

**Key Features:**
- Location transparency
- Distributed query processing
- Two-phase commit protocol
- Heterogeneous database support
- Cross-platform operations

**Architecture Components:**
- Coordinator node
- Data nodes
- Network communication layer
- Distributed catalog
- Query decomposition engine

### Distributed Queries

**Query Processing:**
When a distributed query is executed:
1. Query received at coordinator
2. Query decomposed into sub-queries
3. Sub-queries sent to appropriate nodes
4. Partial results returned
5. Results merged at coordinator
6. Final result returned to client

**Optimization:**
- Minimize network traffic
- Push filtering to data nodes
- Parallel execution where possible
- Cost-based optimization across nodes

### Two-Phase Commit

**Transaction Coordination:**
For distributed transactions:

**Phase 1 - Prepare:**
- Coordinator asks all nodes to prepare
- Each node prepares transaction
- Nodes respond ready or abort

**Phase 2 - Commit:**
- If all ready, coordinator sends commit
- All nodes commit transaction
- If any abort, coordinator sends rollback

**Advantages:**
- ACID properties maintained across nodes
- Consistency guaranteed
- Automatic rollback on failures

### Network Configuration

**Ingres Net:**
Required for distributed database access:
- Configures remote server access
- Defines virtual node names
- Manages authentication
- Handles protocol translation

**Connection Parameters:**
```
vnode::database_name
```

Where vnode is a virtual node name defined in Ingres Net configuration.

## SECTION 17: TROUBLESHOOTING GUIDE

### Common Issues and Solutions

**Connection Problems:**

*Issue:* Cannot connect to database
*Possible Causes:*
- Ingres services not running
- Network connectivity issues
- Incorrect credentials
- Database not started

*Solutions:*
```
ingstat                    # Check if Ingres is running
ingstart                   # Start Ingres if stopped
infodb database_name       # Verify database exists
```

**Performance Issues:**

*Issue:* Slow query performance
*Possible Causes:*
- Missing indexes
- Outdated statistics
- Insufficient cache
- Lock contention

*Solutions:*
```sql
UPDATE STATISTICS tablename;    -- Update statistics
CREATE INDEX idx_name ON table(column);  -- Add indexes
```
Increase database cache size in configuration

**Space Issues:**

*Issue:* Transaction log full
*Possible Causes:*
- Long-running transaction
- Insufficient log size
- Journal not archived

*Solutions:*
- Commit or rollback long transactions
- Increase log file size
- Archive journal files
- Enable dual logging with larger log

**Recovery Issues:**

*Issue:* Database won't start after crash
*Possible Causes:*
- Corrupted transaction log
- Incomplete checkpoint
- System crash during transaction

*Solutions:*
```
rollforwarddb database_name    # Recover from journals
ckpdb database_name            # Create new checkpoint
```

### Error Messages

**E_US0010:**
Database does not exist
- Verify database name spelling
- Check if database was deleted
- Use infodb to list databases

**E_LQ0001:**
Lock timeout
- Transaction held locks too long
- Increase lock timeout setting
- Review application logic

**E_DM0042:**
Cannot allocate disk space
- Check available disk space
- Extend location size
- Clean up old checkpoint files

**Performance Analysis:**

4. Analyze lock contention
5. Review cache hit ratios

**Data Integrity Check:**
1. Run verifydb utility
